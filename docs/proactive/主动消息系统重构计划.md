# 主动消息系统重构计划 — 定时器 → 情绪状态机

> 日期：2026-05-15
> 状态：已实现

## 1. 问题背景

用户反馈主动消息系统存在严重问题：
- **半夜还在发消息**：完全没有时间感知，用户睡觉了照样发
- **不关心用户有没有回复**：发完就忘，不管用户回没回
- **没有正常人思维**：只是在完成定时任务，不是真正在"想"对方
- **消息模板化**：每次都是单条，没有情绪递进

## 2. 根因分析

### 2.1 用户回复感知完全断路（最大 bug）

`StateTracker.update_from_message()` 和 `RhythmManager.record_interaction()` 这两个函数**写了但从没被调用过**。管线收到用户消息时根本没通知主动消息系统。

后果：
- `seconds_since_last` 永远是从 1970 年算起的天文数字
- 系统永远认为"好久没聊了"
- `_is_user_responsive()` 永远返回 True（空历史默认放行）
- 深夜门控也失效（`_get_recent_proactive_count()` 永远返回 0）

### 2.2 发送逻辑是"定时器"不是"人"

每 60 秒检查一次，能发就发，发完就忘。没有"我刚发了消息，等 TA 回我"的概念，没有"TA 没回我，我着急了"的状态机，没有"TA 回了，我开心"的情绪。

### 2.3 三步 LLM 调用割裂

想什么（ConcernEngine）→ 评估要不要发（Evaluator）→ 写出来（Expression）是三个独立的 LLM 调用，互相不知道对方在干嘛。

### 2.4 配置不一致

| 组件 | cooldown | daily_limit |
|------|----------|-------------|
| RhythmManager（硬编码） | 1800s (30min) | 10 |
| ConcernEvaluator（config） | 60s | 20 |

RhythmManager 先跑，所以它的值是实际生效的限制。

### 2.5 死代码

`PerceptionLayer`、`ProactiveDispatcher`、`ConcernEngine._loop()` 从未被使用。

## 3. 重构方案

### 3.1 核心思路：定时器 → 情绪状态机

```
用户消息进入 pipeline
        |
        v
ProactiveService.on_user_message()    ← 新增：接入点
        |
        v
StateTracker.update_from_message()    ← 修复：真正调用
RhythmManager.record_interaction()    ← 修复：真正调用
        |
        v
状态机更新 (IDLE → WAITING → CONCERNED → WORRIED → BACK_OFF)
        |

每 60 秒检查：
        |
        v
状态机当前状态?
        |
        ├─ IDLE: 正常节奏，可以主动发
        ├─ WAITING: 刚发了消息，等回复中 → 不发，等
        ├─ CONCERNED: 等了 10 分钟没回 → 发一条关心
        ├─ WORRIED: 又等了 20 分钟 → 发多条，急切语气
        └─ BACK_OFF: 发了很多都没回 → 用户可能在忙/睡了 → 停止
```

### 3.2 对话状态机定义

| 状态 | 含义 | 允许发送 | 转移条件 |
|------|------|---------|---------|
| `IDLE` | 空闲 | 是（正常节奏） | 发了主动消息 → WAITING |
| `WAITING` | 等回复 | 否 | 10 分钟没回 → CONCERNED |
| `CONCERNED` | 担心 | 是（1 条关心） | 又等 20 分钟 → WORRIED |
| `WORRIED` | 着急 | 是（最多 3 条） | 又等 30 分钟 → BACK_OFF |
| `BACK_OFF` | 停止 | 否 | 2 小时后重置 → IDLE |

**任何状态下，用户回复 → 立即回到 IDLE。**

### 3.3 状态对 LLM 的影响

| 状态 | 传给 LLM 的 hint |
|------|-----------------|
| IDLE | "你想主动找对方聊天。" |
| CONCERNED | "你之前发了消息但对方没回，有点担心。" |
| WORRIED | "你发了好几条消息对方都没回，很着急，想知道对方是不是出什么事了。" |

## 4. 实际改动

### 4.1 `proactive_service.py` — 核心改造

- 新增 `ConversationState` 枚举（5 个状态）
- 新增 `on_user_message(user_id, message)` 方法
- 新增 `_get_conv_state()` — 自动状态转移
- 新增 `_should_send_by_state()` — 状态机决定是否允许发送
- 新增 `_get_state_hint()` — 给 LLM 的情绪提示
- `_run_once()` 改为先检查状态机再检查节奏
- 发送后记录交互、更新状态

### 4.2 `rhythm_manager.py` — 修复断路

- `on_proactive_sent()` 末尾加 `self.record_interaction(user_id, initiator="bot")`
- 让 `_is_user_responsive()` 和 `_get_recent_proactive_count()` 真正生效

### 4.3 `pipeline/__init__.py` — 接入通知

- 新增 `_on_user_message` 回调属性
- `_process_text_message()` 处理用户消息时调用回调

### 4.4 `main.py` — 串联

- `pipeline._on_user_message = proactive_service.on_user_message`

### 4.5 `concern_engine.py` — 读取状态提示

- `_build_concern_user_prompt()` 读取 `context["state_hint"]` 并加入 prompt

## 5. 行为对比

| 场景 | 重构前 | 重构后 |
|------|--------|--------|
| 用户没回消息 | 每 60 秒照样发 | 等 10 分钟→关心→着急→停止 |
| 用户回复了 | 不知道 | 立即回到正常状态 |
| 深夜用户没回 | 没有深夜概念 | 状态机自然进入 BACK_OFF |
| 连续发消息 | 无限制 | WORRIED 最多发 3 条就停 |
| 用户在睡觉 | 一直发到天亮 | 30 分钟后自动停止 |

## 6. 后续优化（未实现）

1. **合并 LLM 调用**：ConcernEngine + Evaluator + Expression 合并为一次调用，减少延迟和 token
2. **清理死代码**：删除 PerceptionLayer、ProactiveDispatcher、ConcernEngine._loop()
3. **统一配置**：去掉 RhythmManager 的硬编码默认值，统一用 config
4. **深夜智能判断**：结合用户历史活跃时段，不是简单的时间门控
5. **情绪记忆**：记住用户对主动消息的反应（积极回复 vs 忽略），调整频率
